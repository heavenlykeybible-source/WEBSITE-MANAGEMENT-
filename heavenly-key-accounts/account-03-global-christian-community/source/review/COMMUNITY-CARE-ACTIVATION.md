# Community Care activation — draft/staging first

1. Keep this work on draft PR #23. Do not merge, deploy production, alter Account 4 or run production SQL without owner approval.
2. In an isolated Community staging database, apply the repository migrations through `0018_community_care.sql` in their existing order. This adds preferences, the seven unapproved readings, prayer history/support, three request state columns and the delivery ledger/triggers. It does not subscribe members or send notifications.
3. Set `COMMUNITY_CARE=enabled` only in that staging Worker after migration. When unset/off, the care scheduler exits without querying the new tables; existing prayer endpoints continue their original behaviour. No production resource IDs or cron settings were changed in this patch.
4. Sign in to Account as the owner/administrator. Open Community Care → Review encouragement readings. Personally check each KJV quotation and suggested prayer, then approve intended items. All are initially unapproved. Pausing a reading prevents future delivery; old notifications remain as history.
5. Using test member accounts, choose daily/weekly notifications and the desired time zone/hour on Prayer → My encouragement & prayer preferences. Verify off/pause. In staging only, set a test preference's due timestamp in the past and run the Worker scheduled handler through the normal local/staging development tooling. Confirm one Community Care notification, correct KJV/prayer labels, no duplicate on repeat, and a future next timestamp. Do not use real member accounts for tests.
6. Create private, public, connection-only and circle prayer requests. Explicitly opt one into a reminder. Verify authentic support, voluntary/coalesced follower notifications, stopping support after audience loss, private closure during timed posting restrictions and moderation-provider outages, private history, connection/circle removal and blocks, testimony privacy, closure, cancellation and global reminder pause. A request's default audience is private; private ministry currently means requester-only, not a staffed counselling inbox.
7. Verify contextual screening in the existing intended moderation configuration. New update text must be screened in enforce mode; do not disable existing checks to make a test pass.
8. Verify the home, Prayer and Account experiences in actual desktop/mobile browsers; check existing feed and radio/navigation continuity. Confirm hourly scheduled delivery and Cloudflare resource budgets with representative load. The automated 1,000-user SQLite test proves functional batching/deduplication only.
9. Submit the staged result and test evidence to the owner. Stop for owner approval before production work.

Disable COMMUNITY_CARE to stop future automatic care delivery and return prayer endpoints to the original implementation. Keep migrated data; do not drop tables as a quick rollback. Disabling the feature does not erase notifications already delivered. Honour individual off/pause preferences as well.

No external AI, email, SMS or push credentials are needed for this in-site version. Adding those channels later needs an actual provider, explicit channel consent, delivery/unsubscribe handling and device testing.

The draft audit adds a partial follower-notification lookup index to the still-pending 0018 migration. If an isolated staging database already applied an earlier draft of 0018, do not rerun its ALTER TABLE statements; add only the new `notifications_care_followup` index using IF NOT EXISTS, or rebuild the disposable staging database. Production migration was not performed.
